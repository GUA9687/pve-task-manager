# 设计取舍与已知限制

## 模板的适用范围

当前布局固定四个机器角色、两张 GPU，机器名/标签也写入生成器。更换 VM ID 已通过私有配置实现；增加机器数量、改变角色名、GPU 数量、多 PVE 节点仍需修改生成器和规则。OpenWrt 未接入。

CPU 小图固定利用率 0–100%、频率 0–4 GHz，适配示例平台；更高频率 CPU 需修改量程。首页温度匹配、网卡和磁盘筛选同样需要检查硬件差异。ARM、AMD GPU、多路 CPU、RAID 控制器没有通用适配承诺。

## 采集不是零开销

系统 exporter 应请求采集；硬件工具在独立线程定时运行。BMC/SMART 保持低频，GPU 和 turbostat 高频仍有开销。所有页面关闭后退回一分钟，能减少开销，但不会完全停止监控。一个请求活跃即可保持高频，当前没有逐用户订阅计数或页面心跳租约。

实时刷新目标 1 秒，受网络、Grafana 请求调度、Python 代理、Prometheus 计算和硬件命令耗时影响，不是严格实时系统。查询共享降低请求数，但 96 图同时渲染仍会消耗浏览器 CPU。

## 历史和可视化

分钟采样的温度/内存是采样时刻快照，不能称为整分钟平均值；短暂峰值可能错过。范围查询可能采用大于一秒的 step，有限像素不能保证展示每个峰值。

路由整条查询选择一个通道；实时缓存缺失时不自动回退或拼接历史。需要跨越 30 分钟范围时显示的是低频历史。时间保留、大小保留、索引、WAL 共同决定容量，当前没有硬配额机制。

## 安全边界

- 预期在可信管理网使用。示例 Grafana、exporter 和模式查询使用 HTTP；Basic Auth/Bearer 在 HTTP 上不提供加密，应通过隔离网络或自行配置 TLS 保护。
- Prometheus 两个实例仅 loopback；代理仅接受本机 PromQL，远程仅能带令牌读取 `/mode`。不要通过不受控反向代理把 loopback 接口暴露出去。
- Linux 硬件采集和自适应控制器当前以 root 运行，前者访问硬件、后者替换配置并发送 HUP。systemd 加固选项有帮助，但不是权限隔离的完整证明。
- Windows exporter 模板使用来源 IP 防火墙约束，没有配置 exporter 身份认证；部署者需要检查现有规则。
- 备份、build/、私有 inventory 和运行日志不应公开。仓库自带的扫描只做有限静态检查，不能替代人工审阅。

## 后续可改进方向

可将固定角色/设备筛选改成完整 inventory 驱动；以最小权限分离硬件和控制器；支持 TLS、指标预算告警和硬限额；为长短时序做明确聚合与拼接；扩展多路 CPU/AMD GPU；建立全新环境的可重复端到端安装测试。这些都是后续方向，当前版本没有声称已经实现。
